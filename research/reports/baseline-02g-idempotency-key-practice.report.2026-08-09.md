# Baseline 02g — Idempotency Keys at OpenAI, Anthropic, and Google

*Narrow leaf under `baseline-02`, feeding `AC-016`'s placement fork (header
vs body/query) at Gate C. Covers the mandatory modern-AI-vendor evaluation.
Run 2026-08-09; evidence from published OpenAPI/discovery specs, vendor doc
pages, the AIP repo, and shallow clones of all four official SDKs.*

## 1. OpenAI API — no idempotency mechanism

`[FACT]` OpenAI's published OpenAPI spec
(https://raw.githubusercontent.com/openai/openai-openapi/master/openapi.yaml,
fetched 2026-08-09, ~2.8 MB) contains no idempotency key of any kind: the
string `idempot` appears on exactly 4 lines, all prose in certificate
endpoint descriptions ("You can atomically and idempotently activate up to
10 certificates at a time"). The only `in: header` parameter anywhere in
the spec is `openai-beta`.

`[FACT]` The closest header is an **anti**-idempotency header.
`X-Client-Request-Id` (developers.openai.com API reference introduction):

> "Along with the server-generated `x-request-id`, you can supply your own
> unique identifier for each request via the `X-Client-Request-Id` request
> header. … **Make this value unique per request.**"

Its stated use is support lookup after timeouts — tracing, not
replay-safety. "Unique per request" is the opposite of idempotency-key
semantics (reuse the same key on retry).

`[FACT]` The production-best-practices guide has no mention of
retries-with-idempotency or duplicate-request handling.

*Absence caveat: established from the published spec plus two fetched doc
pages, not an exhaustive site search.*

## 2. Anthropic API — no idempotency mechanism

`[FACT]` platform.claude.com's errors page does not contain the word
"idempotency". It documents automatic retries *without* any key: *"The
official SDKs automatically retry transient failures (such as connection
errors, rate limits, and 5xx server errors) with exponential backoff,
twice by default, honoring the `retry-after` header when present."*

`[FACT]` `request-id` is a **response** header (support lookup), read but
never written by the SDKs (`ats/src/core/error.ts:35`).

`[FACT]` Batches `custom_id` is result-matching, not deduplication —
docstring verbatim: *"Use the `custom_id` field to match results to
requests."* The one "idempotent" mention in Batches refers to GET polling.

## 3. Google Gemini API — no idempotency mechanism

`[FACT]` The authoritative discovery document
(`generativelanguage.googleapis.com/$discovery/rest?version=v1beta`,
revision 20260806): case-insensitive `idempot` count **0**; no `requestId`
global or per-method parameter. The Gemini API does not implement AIP-155
despite being a Google API.

## 4. Google Cloud / AIP-155 — request-message field; over REST a QUERY parameter

`[FACT]` AIP-155 is active guidance (`state: approved`; last
content-bearing change 2024-01-08). Verbatim:

> APIs **may** add a `string request_id` parameter to request messages …
> - Providing a request ID **must** guarantee idempotency.
> - If a duplicate request is detected, the server **should** return the
>   response for the previously successful request …
> - APIs **may** choose any reasonable timeframe for honoring request IDs.
> - The `request_id` field **must** be provided on the request message to
>   which it applies (and it **must not** be a field on resources
>   themselves).
> - Request IDs **should** be able to be UUIDs … annotated
>   `(google.api.field_info).format = UUID4`.

`[FACT]` **No payload fingerprinting.** AIP-155 defines no behavior for
"same key, different body" — unlike Stripe (and unlike `AC-016`, which
requires fingerprint-and-reject).

`[FACT]` **Correction to the common "body field" framing: over REST it is
usually a query parameter.** On standard create methods the resource
occupies the HTTP body, so `request_id` transcodes to the query string.
Verified against Cloud Deploy's discovery document (revision 20260729):
every `*.create` method carries `requestId` with `"location": "query"`.
Its description carries the only concrete retention datum found on any
surface: *"The server guarantees that for at least 60 minutes after the
first request."*

`[FACT]` **No header guidance anywhere in the AIP corpus** — zero hits for
`idempotency-key` across the repo; the word "header" does not appear in
0155.md. No newer Google guidance moves the key to a header.

`[FACT]` AIP-4235 (approved 2024-03-07) makes the key client-generated by
default and mandates retry-reuse: *"Client libraries **must** reuse
automatically populated values for retries of the same request."*

## 5. The Stainless SDK layer — header machinery, present but dormant

All four official SDKs (openai-node, openai-python,
anthropic-sdk-typescript, anthropic-sdk-python) ship identical
Stainless-generated idempotency machinery, and **none activates it**:

- `[FACT]` A public-but-undocumented `idempotencyKey` request option
  exists (*"A unique key for this request to enable idempotency"*), with
  default key generators (`stainless-node-retry-<uuid4>`,
  `stainless-python-retry-<uuid4>`) and retry-reuse logic (the key is
  generated once and reused across attempts, non-GET only).
- `[FACT]` The header name is never assigned: `idempotencyHeader` /
  `_idempotency_header` has zero assignments in all four repos, and the
  send site is guarded on it — so **nothing is emitted on the wire**, and
  a caller-supplied `idempotencyKey` is silently dropped.
- `[FACT]` The only occurrence of `'Idempotency-Key'` in any repo is a
  test that overrides the property to exercise the path
  (`openai-node/tests/client-behavior.test.ts:13`).
- `[INFERENCE]` If either vendor ever enables it, the placement is a
  Stripe-style request header. The dormant machinery is the exact
  functional twin of Google's AIP-4235 auto-populated `request_id` —
  except Google's is switched on and the AI vendors' is switched off.

## Net

None of the three modern AI vendors documents a public idempotency
mechanism on its main API, so their shipped practice supports **neither**
placement: OpenAI has none (and its one user-supplied header demands
uniqueness per request); Anthropic has none (SDKs auto-retry non-GET
requests with no key on the wire); Gemini has none. The only **active**
guidance among the four surfaces is Google's AIP-155 — a request-message
field that lands as a **query parameter** over REST, with UUID keys,
service-chosen retention (60 minutes in practice at Cloud Deploy), and
**no payload fingerprinting**. The header camp's support is Stripe, the
expired IETF draft's shape, UCP's signed `idempotency-key` header
(`baseline-03d`), and the dormant-but-header-shaped Stainless machinery in
both AI vendors' SDKs — latent plumbing, not shipped behavior.
