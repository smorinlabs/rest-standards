Conduct a deep, current best-practice survey to determine the normative security and operational principles for a new public, implementation-neutral REST-over-HTTP design standard.

Exact scope: transport security; authentication and authorization patterns, including OAuth/OIDC, token handling, API keys where appropriate, least privilege, tenant/object/function-level authorization, and security-error behavior; abuse and resource-exhaustion resistance; rate limiting and quota communication; overload behavior; client retries, Retry-After, exponential backoff, jitter, timeouts, and retry safety dependencies; operational rollout of compatible and incompatible versions; deprecation, sunset, migration communication, and support windows; request/correlation identifiers, distributed trace context, metrics, logs, audit events, diagnostic exposure, and privacy; and webhook/event delivery, including signing, verification, replay resistance, delivery identifiers, acknowledgement, asynchronous processing, duplicates, ordering, retries, recovery, and versioning operations. Compare official operational guidance from Google, Microsoft/Azure, GitHub, Stripe, and other materially relevant API providers.

Do not re-decide URI/resource modeling, HTTP method/status semantics, validators, or caching; JSON representation shapes, Problem Details extensions, pagination/filter syntax, OpenAPI workflow, or compatibility taxonomy; application-level Idempotency-Key format, fingerprint, retention, and replay response behavior; bulk request contracts; or asynchronous job resource shapes. This thread owns retry/backoff and overload policy but must consume idempotency behavior as a dependency. It owns deprecation/sunset operations but consumes compatibility/versioning definitions. It owns webhook transport/security but not the generic asynchronous-operation resource model.

Context and constraints:

- The output will inform a durable public standards document, not a specific deployment.
- There is no prescribed language, framework, cloud, identity provider, API gateway, or telemetry vendor.
- The primary use case includes public or cross-trust-boundary APIs receiving untrusted input and credentials and potentially exposing sensitive data; account for injection and unsafe downstream API consumption without inventing regulatory requirements.
- Recommendations must support independently evolving clients and services under retries, partial failures, abuse, overload, incident response, and multi-tenant authorization.
- Prefer open standards and current security BCPs while acknowledging deployed vendor conventions and migration constraints.
- Discuss GraphQL, RPC, streaming, or messaging only where needed to clarify this standard's boundary or an interoperability point.

Research requirements:

1. Begin with current primary and authoritative sources. At minimum, verify RFC 9700 and the current OAuth/OIDC security landscape; applicable TLS guidance; OWASP API Security Top 10 and its methodology limitations; RFC 9745 and RFC 8594; Retry-After and 429 semantics in current HTTP standards; the current IETF RateLimit draft status; W3C Trace Context; relevant OpenTelemetry specifications; RFC 9421; and official webhook guidance. Check for updates, obsoletions, errata, newer BCPs, and active drafts at research time.
2. Compare current official Google, Microsoft/Azure, GitHub, Stripe, and other materially relevant vendor guidelines specifically for security and operational behavior. Do not use their unrelated URI or JSON style rules to reopen other threads. Identify both convergence and product-specific divergence.
3. For every material claim, provide a direct URL and identify source authority, version or publication/update date, access date where available, and currency: BCP/published standard/current registry, active draft, expired or obsolete item, official security guidance, official vendor convention, or secondary evidence. Never present an Internet-Draft or proprietary header as a published standard. Label sourced facts, inferences, recommendations, and proposed project policy distinctly.
4. Explicitly surface conflicts. Explain whether each disagreement reflects threat model, public versus internal API posture, browser versus service client, provider architecture, historical migration, or true standards conflict. Recommend which principle should govern and why; use conditional recommendations when threat models differ.
5. Identify canonical patterns and anti-patterns with concrete failure modes. Include at least: bearer tokens in URLs, long-lived broad tokens, authentication mistaken for object authorization, predictable identifiers treated as access control, mass assignment/excessive data exposure, unlimited expensive operations, undocumented proprietary rate headers, retrying every failure, retries without jitter or idempotency awareness, leaking sensitive diagnostics, unbounded high-cardinality labels, propagating untrusted trace fields without limits, silent breaking shutdowns, indefinite deprecation, unsigned webhooks, signature verification after JSON parsing, replay windows with no delivery deduplication, slow synchronous webhook handlers, assuming exactly-once delivery, and assuming event order. Correct or reject any item not supported by evidence.
6. Address contested choices explicitly: OAuth/OIDC versus API keys by client/use case; opaque versus self-contained access tokens; token sender-constraining; scope and audience design; rate-limit header policy while the IETF work remains a draft; 429 versus overload 5xx behavior; retry eligibility and budgets; externally supplied versus generated correlation IDs; trace propagation and privacy; minimum telemetry contract; deprecation notice channels and support windows; webhook HMAC schemes versus HTTP Message Signatures; key rotation; replay tolerance; ordering guarantees; and dead-letter/redelivery access.
7. For observability, separate what an API standard should require on the wire or in public documentation from internal implementation guidance. For security, separate universal baseline controls from risk-based controls whose strength depends on data sensitivity, client type, and threat model.
8. State assumptions about client types, browser involvement, tenancy, data sensitivity, regulatory context, availability goals, traffic shape, threat actors, event volume, and operational staffing. Explain which recommendations change when those assumptions change.
9. State confidence for every major finding and final recommendation, with the basis. Lower confidence for unsettled drafts, vendor-only convergence, or guidance whose threat model is unclear.

Output:

- An executive recommendation naming the concrete security and operational principles to design against.
- A source-and-currency matrix with direct URLs, versions/dates, authority classification, and known limitations.
- A threat-and-failure-model summary tying recommendations to risks rather than popularity.
- A comparative matrix of official vendor practices limited to authentication/authorization, rate limits, retries, deprecation, observability, and webhooks.
- A conventions/patterns section and a separate anti-patterns section.
- A proposed normative-principles table. Give every principle a stable provisional ID, `MUST`/`SHOULD`/`MAY` strength, concise rule text, rationale/threat mitigated, applicability or exceptions, externally observable requirement versus internal control, evidence URLs, and confidence. The set must be concrete enough to seed a standards document and conformance checklist.
- A conflict-and-open-questions section separating research-resolvable questions, risk-based conditional choices, and organization policy decisions.
- A short dependency handoff to the HTTP-semantics and API-contracts research without answering those threads' questions.
- A final overall confidence statement and assumptions that would invalidate or materially change the recommendation.

The research is complete only if it recommends an actionable, risk-grounded baseline for production APIs and explicitly distinguishes standards, BCPs, drafts, and vendor conventions rather than producing a generic security checklist.
